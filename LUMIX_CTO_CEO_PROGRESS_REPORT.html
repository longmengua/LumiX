1. 核心架構：資產與提款的安全分層

下圖描述已實作的測試網流程設計；完整流程尚未以實際測試網端到端驗證。

已認證使用者 → 應用程式介面（API，Application Programming Interface）/ WithdrawalOrchestrator → 資產保留 → 風控／人工覆核 → 最終風控閘 → 簽章閘道 → 獨立 lumix-signer（僅 Sepolia） → Ethereum RPC 廣播 → 交易收據與最終性對帳 → 保留扣轉與不可變帳本日誌 → 已完成（COMPLETED）

架構決策

  • 主應用程式不持有原始私鑰（raw private key）、助記詞（mnemonic）或種子片語（seed phrase）。
  • withdrawals 是唯一提款主表；地址、風控、覆核、簽章與鏈上交易表僅保存其外鍵證據。
  • 只有交易收據成功且最終性證據成立，才能進帳本結算；廣播不確定時維持 BROADCAST_UNKNOWN（廣播結果未知），不重簽、不解鎖本金（principal）。
  • 所有資產異動（mutation）均經帳本邊界（ledger boundary）；修正必須新增沖銷／調整（reversal / adjustment），不能覆寫歷史。

3. 受控操作流程：從申請到完成
已申請（REQUESTED）→ 資金已保留（FUNDS_HELD）→ 等待風控（RISK_PENDING） → 人工覆核／已核准／風控暫停／已拒絕 已核准（APPROVED）→ 最終風控檢查 → 等待簽章 → 簽章中 → 已簽章 → 廣播中 → 廣播結果未知／已廣播 → 等待確認 → 已完成（COMPLETED）

系統處理與控制要點

  1. 使用者建立提款時，必須提供一致的請求本文（body）或請求標頭（header）冪等性金鑰（idempotency key）。
  2. 系統先驗證可用餘額並建立 WITHDRAWAL_HOLD（提款保留）；不直接扣帳。
  3. 風控拒絕或需人工處理時，不可繞過覆核；申請人（request owner）不能自行覆核。
  4. 簽章前重新驗證核准資料雜湊（approval payload hash）與最終風控；風控、核准或最終性有任何未知狀態，一律不放行。
  5. 鏈上交易收據最終確認後才扣轉保留並寫入不可變帳本日誌；收據失敗會保留燃料費（gas）證據並釋放本金保留。

5. 建議工作與主要缺口

受控 Sepolia 驗證

準備可審核的測試環境，執行 ETH／USDT 手動 E2E，確認鏈上結果與帳本一致。

工程：補強高風險測試

優先驗證交易序號（nonce）併發、廣播歧義、收據失敗釋放、結算當機復原，以及核准證據到角色型存取控制（RBAC，Role-Based Access Control）的實際映射。

治理：正式託管路線

評估並審核硬體安全模組（HSM，Hardware Security Module）、多方安全運算（MPC，Multi-Party Computation）或外部託管等方案，以及雙向傳輸層安全（mTLS，mutual Transport Layer Security）、機密隔離與復原能力。

尚未開放的產品功能

  • 正式 Mainnet 入金／提款與資產信用入帳。
  • 公開行情資料管線／傳輸（market-data pipeline / transport）、撮合執行（matching execution）、正式結算與費用收取執行能力。
  • 完整正式環境遙測（telemetry）、告警（alerting）、備份還原／災難復原（DR，Disaster Recovery）演練、負載／混沌測試與人類正式上線簽核。
